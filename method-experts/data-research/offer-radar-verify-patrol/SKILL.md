# 福利雷达核实巡查三层管线（专家模式）

- 领域：数据与投研
- 来源：数字生命卡兹克（@Khazix0918）长文自述其 AIHOT「Token 羊毛」子站（aihot.news/free-tokens）的生产系统，收录于西瓜小本本第 417 条；vault 笔记《Token 羊毛：AIHOT 免费额度雷达与核实巡查管线笔记》
- 核验状态：站点 2026-11-09 实读在架，页面自述的收录与巡查规则与长文逐项一致；AIHOT 仓库 9,672★ 已于 2026-11-06 核实（与文中「近 1 万 Star」相符）；管线内部实现（轮询频率、判定口径等）为作者自述其自有系统，未独立核实；月活、单日可领金额等数字为作者自述/时点数
- 适用：给一类「变化快、假货多、过期即无价值」的公开信息（厂商免费额度/限时活动/公告类条目）搭一条自动发现→核实→巡查的监控管线，只做信息监控，不发生任何交易

## 定位

这个专家是「情报站的编辑部流水线」：信奉噪声与信号取决于需求端——为新闻写作的剔除规则（中转站、返利、付费用户专享不算新闻）反转过来，正是识别真福利的规则。它的成本观很明确：发现要宁滥勿漏（多收一条只多一次便宜的模型调用，漏掉的永远看不到），核实要贵但只花在刀刃上（靠触发门槛唤醒，而不是全量核查），变更监测不用整页 diff，用上架时照抄的原话做锚点机械比对。最终清单要过人手确认才对外，Agent 负责跑腿与初筛，人负责拍板。

## 何时用 / 何时不用

- 用：监控对象是厂商公开活动/额度/公告这类时效条目，来源杂、假站与过期信息多，需要「发现→核实→持续巡查到下架」的完整链条；同法可平移到限时促销、政策公告、版本发布等公开信息监控。
- 不用：需要真实交易或下单（本模式只到信息监控为止，本区硬边界）；条目变化慢、人工订阅官方渠道就够的场景（整套管线是杀鸡用牛刀）；无法核实到第一方页面的封闭渠道（核实层的前提是厂商页面公开可达）。

## 方法步骤

1. **定信源池**：厂商官方账号与活动页 + 专挖这类信息的活跃账号 + 社区合集帖，三类都要有；信源池本身定期增删。
2. **雷达层（每小时一轮）**：先过一张故意撒宽的关键词网做预筛（如 免费/白嫖/薅/羊毛/额度/赠金/签到/限免，含英文 free/credits），宁滥勿漏——预筛只求不漏，误收的成本只是一次短而便宜的模型调用。
3. **雷达层判定**：候选交给大模型做确定性判定——把文本里提到的每个活动逐个列出，逐个判「算不算目标条目」，不算的必须给理由（中转站/返利/只给付费用户的在此毙）。判定口径写死，不许模型自由发挥。
4. **核实触发门槛（三居一才唤醒）**：厂商自己的账号说了、或两个不同来源独立在说、或帖子直链厂商自己的页面——三者居一才唤醒核实 Agent。门槛之外一律不查，这是核实成本可控的关键。
5. **核实只认第一方**：核实 Agent 只采信厂商页面，且必须从厂商官网首页或官方账号一路点到活动页确认真伪——假官网、仿冒活动页很多，只看链接域名或截图不算核实。核实不了的条目先标「待官方确认」、不计入对外统计，限期（原系统为 3 天）仍核实不了就下架，不许无限期挂着。
6. **「值得领」价值关**：核实为真还要再过价值关，全毙清单——只能用老旧模型的（如文中点名的 GLM-4.7、DeepSeek V3 级）、把分项数字加总成虚增总数的（如「每模型送 100 万」汇总成「送 7000 万」）、返利与邀请链接、API 中转站、二手积分、共享账号、接码多开、只给付费用户的、要先充值才送的。
7. **上架留锚点**：每条上架时，从厂商页面照抄 1–3 句原话（送多少、怎么领、到哪天）存为锚点，与条目绑定。
8. **巡查层（每日两次脚本比对）**：脚本对照锚点原话——连续两次找不到原话、或页面新出现「暂停」「结束」等字眼，立即派 Agent 复查该条目（下架、改链接或改规则）。
9. **夜间全量巡检 + 次晨人审**：每晚另有 Agent 按巡检手册把在架条目逐条重过一遍；次晨把新上架与变更（换链接、改规则）列成清单交人确认后才对外更新——批奏折式人审，Agent 不自行动条目。另设公开提报入口，漏收与报错可由用户提报回流。

## 提示词与模板

无固定提示词全文，按方法步骤执行。要照搬的是三份结构件：

```text
雷达判定输出：逐条列出候选 → 每条给「算 / 不算」+ 不算的理由（理由须命中毙除清单条目）
核实触发：官方发声 ∨ 双独立源 ∨ 直链厂商页（三居一才唤醒核实 Agent）
锚点记录：{条目, 厂商页 URL, 原话 1–3 句（送多少/怎么领/到哪天）, 抄录日期}
「值得领」毙除清单：老旧模型 / 虚增汇总数字 / 返利邀请 / 中转站 / 二手积分 / 共享账号 / 接码多开 / 先充后送
```

## 验收标准

- 雷达轮询按小时跑，关键词网保持宽口径；判定输出逐条带结论，不算的逐条带命中清单的理由。
- 没有任何条目绕过核实触发门槛直接上架；每条在架条目的核实路径可回溯到厂商第一方页面（从官网首页或官方账号点达）。
- 每条在架条目都有锚点原话存档；巡查脚本每日跑满两次，锚点消失或出现结束字眼的条目都有 Agent 复查记录。
- 夜间全量巡检有产出清单；对外更新只发生在次晨人工确认之后。
- 全程无任何交易、充值或下单动作，产出只到信息清单为止。

## 边界与风险

- **本区硬边界**：本方法只用于信息的研究、监控与巡查；不下真实订单、不动用真实资金；涉及交易需用户另行批准并先定资金上限与风控规则。
- 单一来源风险：整条管线是作者对自有生产系统的自述，除站点在架与页面规则已实读核对外，内部实现细节（轮询频率、判定准确率、巡查命中率）未独立核实，引用时标注作者口径。
- 效果数字打折：文中月活、「写作时今日可领 201 元」等为作者自述或时点数，不可当作持续事实引用。
- 假站风险是常态：核实层「从官网首页一路点达」不可省，搜索引擎结果页与聚合帖里的链接都不能直接当厂商页采信。
- 价值关是编辑立场不是客观标准：毙除清单反映收录方的取舍，迁移到其它监控主题时要按自己的需求重写清单，而不是照抄福利口径。
