# 长篇连载一致性工程（专家模式）

- 领域：Agent 工程
- 来源：lingfengQAQ/webnovel-writer（Claude Code 插件），经 Denzii（@denziideng）帖介绍，收录于西瓜小本本第 315 条；vault 笔记《Webnovel Writer：长篇连载一致性工程笔记》
- 核验状态：仓库 7,845★ / 1,269 forks / GPL-3.0、359 commits、最近提交 2026-10-22，机制经仓库 README 逐项核对属实（2026-11-05）；「几百章不崩设定」「200 万字量级」为仓库自述，无第三方实测
- 适用：任何长篇/连载型生成生产（小说、系列课程、长报告、多期内容），核心问题是「写到后面忘了前面、设定自相矛盾」时

## 定位

长篇崩坏不是文笔问题，是账目问题。解法：把「已发生的事实」当账本管——只有一个事实源，动笔前先立合同，写完必须提交入账，审查不过不许往下写。写作可以自由，事实必须过审。

## 何时用 / 何时不用

- 用：连载/系列化生产，单元之间有强事实依赖（人物、设定、伏笔、数据口径）；多 Agent 分工起草与审查
- 不用：一次性短内容（合同与提交链是 overhead）；事实无累积的独立单元生产（各篇互不引用时，普通审核台足够）

## 方法步骤

1. **立单一事实源**：所有设定与已发生事实只存一处（原项目 `.story-system/`）。状态文件、检索索引、章节摘要、长期记忆、展示面板全部是从主链派生的**只读视图**，不许反向写；派生同步失败要有投影日志能定位哪一路没跟上。
2. **写前合同**：每个生产单元动笔前，先从事实源刷新本单元的「合同」（本单元可用的事实、必须回收的伏笔、禁区），再由 context 环节生成写作任务书。
3. **起草与多维审查**：起草放开写；审查由独立 reviewer 从多个维度打（原项目：爽点/一致性/节奏/OOC/连贯性/追读力），其中**一致性类问题定为 blocking——不通过则阻断**，不许进入下一单元；其余维度只记录不阻断。
4. **写后提交**：单元定稿后由 data 环节提取本单元产生的新事实，生成一次正式提交（原项目 `CHAPTER_COMMIT`）驱动各路投影更新；没提交的事实等于没发生。
5. **终检与备份**：润色后加一道风格终检（原项目是 Anti-AI 终检），然后备份本单元产物。
6. **可信断点续跑**：重跑同一单元时，跳过已可信完成的环节（正文/审查/提交/备份分别记账），只从失败点继续，不重写已可信部分。
7. **经验沉淀**：把本项目验证过的有效写法存进项目长期记忆（原项目 `/webnovel-learn`），后续单元自动受益——生产系统自带学习环。
8. **配套工具面**：查询口（按角色/伏笔/实体关系查事实源）、只读面板（看全局状态）、体检命令（按阶段查缺项，原项目 `/webnovel-doctor`）。

## 提示词与模板

无单条提示词；核心工件是三件：事实源的存储结构（合同/提交分离）、审查维度表（含哪几维是 blocking 的定义）、提交格式（新事实如何入账）。原项目另带 37 个中文网文题材模板与可插拔检索层（Embedding＋Rerank 可配，无 Key 自动退回 BM25）作参考实现。

## 验收标准

- 随机抽一个早期事实，中途任何单元引用它时与事实源一致（查得到、没变形）。
- 故意在一个单元里写一条与事实源冲突的设定，审查环节能以 blocking 拦下。
- 杀掉一次运行后重跑，已可信环节被跳过、只从断点续（看运行记录）。
- 每个派生视图都能追溯到主链的某次提交；投影日志无未处理的不同步。
- 体检命令能列出当前阶段的缺项（缺合同、缺提交、缺备份）。

## 边界与风险

- 效果口径（几百章不崩、200 万字）为项目自述、未实测；机制可借，效果不要当承诺引用。
- GPL-3.0：把代码本体嵌进闭源产品前先看许可证义务；只借机制设计不受此限。
- 仓库 README 赞助区有大量 API 中转商广告，与功能无关，引用仓库时剥离。
- 事实源若初期建得潦草，后面所有单元都在错账上累积——初始化（原项目 `/webnovel-init` 的深度初始化）是全系统最不能省的一步。
