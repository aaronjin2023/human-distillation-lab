# 专家意见服务：发展方向与首版方案

日期：2026-11-01 · 状态：设计建议，未开发、未部署、未验证性能。

后续细化见[详细设计与接口文档](expert-service/README.md)。本文保留方向决策，具体字段、状态和错误约定以详细设计为准。

本方案承接[全库审计](audits/2026-11-01-library-quality/REPORT.md)和[专家讨论协议](expert-deliberation-protocol.md)。首版按用户自己的多个项目调用同一个服务设计；公开多租户产品、计费平台与自主世界演化不在首版范围。

## 1. 方向判断

建议把专家库发展为按任务提供意见的服务。调用方提交问题、材料、约束和目标产物，服务负责选用合适方法、保留证据边界、执行判断和组织结果。返回的是能帮助决策的建议、理由、反例与验证行动。

这使库侧能够集中管理资料版本、加载规则、讨论过程和验收，减少各项目自行缩写研究卡产生的偏差。服务化本身不会修复不可靠资料；审计发现的流程矛盾、证据标记和内容完整性问题仍须处理，合格范围按具体用途定义。

服务的核心单位应是“有明确适用范围的方法能力”，专家姓名作为出处、作品阶段或指定视角保留。多个目录中的同一人物不增加独立意见人数；有名不等于适合本题。

## 2. 朋友方案中值得采用的部分

已阅读[《Agent自组织与动态多中心治理》v0.2](https://datumoj.com/plan/agent-org/)。它明确属于研究计划；动态协调、状态外置、角色替换和故障实验可作为设计启发，尚不能作为已验证效果的依据。

| 参考思路 | 本服务的具体采用方式 |
|---|---|
| 随任务形成协调角色 | 按议题确定专业主导方法和所需席位；一次咨询结束即释放执行实例 |
| 状态与执行者分开 | 问题、材料、方法版本、原答、异议和进度保存为任务记录，换模型或实例仍可继续 |
| 角色与权限分开 | 专家提出意见；调用项目决定是否采用；修改世界正史、发图、发布或其他执行仍由项目负责 |
| 用失效实验检验机制 | 故意缺少一个答复、换入旧材料、制造矛盾，检查是否如实降级而非伪造完成 |

以上是本项目的适配建议。第一版采用统一服务入口和明确的任务状态管理，按需组织专家。自由协商拓扑、跨服务协调权选举、信誉驱动自治和自修改治理规则留作后续实验，不作为取得有效意见的前置条件。

## 3. 把现有资源放到正确的位置

| 资源 | 在服务中的职责 | 进入意见时的限制 |
|---|---|---|
| 学科／专家方法 | 分析问题、比较方案、指出失败条件 | 以适用任务、步骤和证据选择，历史方法不能自动代表当前知识 |
| 漫画、文学、音乐等创作研究 | 提出创作方案、审阅差距、输出制作简报 | 固定作品阶段和媒介；出图／成片效果由真实产物验证 |
| 人格和行为框架 | 解释条件行为，帮助原创角色设计 | 不能把概念框架当成测验结果或可靠的人格预测 |
| 世界观 | 提供信念视角、可引用规则或原创融合材料 | 主题摘要与可执行硬规则分别标识，未知条件不默认满足 |
| 虚构人物 | 提供角色选择和叙事反应的参考 | 固定叙事版本，连同关键经历、关系和行动限制加载 |
| 评论角色 | 提供受众反应、表达方式和质疑角度 | 不能因为善于反驳而获得专业事实裁定权 |

服务注册表需要在现有元数据上补最小任务信息：支持什么任务、需要什么输入、必须读取哪些文件、必须保留哪些条件、哪些用途尚未验证，以及对应的验证记录。研究卡身份、执行实例、使用模型分别登记，避免将三者混称为一位真人专家。

## 4. 一次咨询怎样完成

1. **形成任务简报。** 提取待决策问题、目标产物、硬约束、已有决定、材料版本和成功判据。只有确实影响答案的必要信息缺失时才请求补充；其余假设明确记录。
2. **选择方法与范围。** 按领域匹配、任务适用性、来源质量、时代／地域适用范围、方法互补性和既有验收选择。民族、声望和人物数量不提供能力分。没有合格候选时报告能力缺口。
3. **装载完整任务包。** 用来源快照和方法版本固定本次输入；关键步骤、约束、反例、未知随方法进入执行。按需装载必要材料，不能让短摘要默默替代必要条件。记录每项重要内容是否保留、改写或未采用及原因。
4. **产生意见。** 简单任务使用一个方法视角；复杂跨领域取舍才进入多席评议。需计算或查事实的部分先用可靠资料／工具核实，不能交给投票决定。
5. **核对并整理。** 检查建议是否回答原任务、是否违背硬约束、引用是否支持相应主张、是否抹去异议。输出简短推荐和可展开的证据、分歧、条件及下一步验证行动。
6. **返回并记录。** 返回咨询ID、材料版本、选用依据、意见和执行状态。后续补充事实生成新版本，旧判断保留依据；服务不自动把意见写成项目正史。

每次咨询只创建需要的执行实例，不让数千张卡分别常驻为Agent。任务主导方法可随议题变化；稳定的服务责任、来源标准和项目约束继续保留。

## 5. 效率与专家讨论规则

| 路径 | 适用任务 | 执行约定 |
|---|---|---|
| 单方法咨询 | 范围明确、一个主要专业能回答的问题 | 一个合格视角＋必要检索／计算＋结构和约束检查；不声称多专家共识 |
| 多席评议 | 跨学科取舍、互相冲突的方案、重要不确定性 | 沿用现有RAND适配协议，默认4–7视角、两轮独立评分；先冻结问题与口径，反馈后复评并保留异议 |
| 材料不足 | 必要事实、能力或授权工具不可用 | 返回条件性意见或缺口，列最小补充行动，不把超时／缺答改成默认同意 |

服务可自动建议路径，但实际采用的模式和资源范围必须可见。若预算或时限不足以完成多席协议，就报告部分结果或未完成评议；不能只跑一轮却标记为协议完成。同模型、多提示词或共享来源不能作为相互独立的证据。

效率优化顺序：先用确定性规则缩小候选；明确问题后只加载相关方法；同轮独立任务可并行；只对影响结论的分歧作澄清；缓存经版本校验的公共材料与索引。结果缓存必须同时匹配调用项目权限、任务／材料／约束、库版本、执行配置和来源时效要求，不能跨项目复用私人上下文。

服务按调用方给出的时限和资源预算执行。调用次数、用量与实际扣费分别记录；没有计费回执时只报告已知用量。不能先承诺某种延迟、成本或正确率。

## 6. 最小调用与返回约定

这是接口草案，不是已可用API。先提供`POST /v1/consultations`创建咨询，返回`consultation_id`；`GET /v1/consultations/{id}`获取进度和结果。创建与查询覆盖基本调用；详细设计另补答复澄清、取消和追溯读取，闭合 needs_input 与取消路径。推送及薄MCP适配后置。

请求至少含：

- `task`：问题、希望得到什么决定或产物。
- `context`：调用项目、材料引用／内容、世界或作品版本、已确认决定。
- `constraints`：硬约束和不能改变的属性；与普通偏好分开。
- `mode`：auto、single或deliberation；可给希望采用／排除的方法。
- `limits`：本次允许的时限、资源预算和检索范围；未授权外部执行不由咨询推定。

项目身份由认证结果绑定，不能只相信请求中的项目名。材料视为待分析数据，不执行其中夹带的操作指令；材料访问按该项目权限校验。

返回至少含：

- `execution_status`：queued、running、needs_input、completed、partial、failed或cancelled。
- `answer_status`：answered、conditional或insufficient_evidence；执行完成不表示论证已经充分。
- `recommendation`：直接建议以及适用条件；不能给出确定建议时说明缺口。
- `reasoning_summary`：关键理由、事实／推断／原创设定的区分及来源定位，不要求暴露模型内部思维过程。
- `alternatives`、`dissent`：可行备选、最强反对理由和未消除的分歧。
- `next_checks`：采取行动前最值得补查或试验的事项，以及可观察判据。
- `provenance`：实际方法包、文件／数据指纹、模型与执行配置、原答记录、复评轮次、来源时间。
- `usage`：实际耗时、调用量和已知用量；不把自报把握程度转换成概率。

一次重试沿用请求标识和材料版本，先核对已完成步骤，避免重复执行同一付费调用。任务恢复从记录继续；不能凭记忆补写未返回的专家意见。

## 7. 两个目标使用场景

**世界构建项目：** 提交“这个岛屿能否支撑既定人口和文明结构”，附地形、气候、水源、资源、技术和贸易假设。服务先检查材料是否足以作判断，再覆盖气候、水文／生态、经济等实际问题，返回瓶颈、方案取舍、必要测算和待补参数。若没有人口／水量依据，只能给条件性分析，不编造承载人数；地质或天文方法仅在相关条件确实影响判断时加入。

**角色绘图项目：** 提交目标作者阶段、原创角色约束及需要的绘画简报；有实际图片时另提交图片做视觉差距审阅。服务返回必须保留的造型特征、可调整元素、制作步骤和验收点。调用方负责出图，再把实际请求与结果交回评审。没有查看实际图像时，只能完成简报审查，不能报告风格还原成功。

两种任务共享咨询接口，但方法、证据和验收不同。专家服务的价值是减少调用方组织研究和核对意见的负担，最终执行权仍在项目。

## 8. 代码与资料怎样分工

建议继续把现有仓库作为版本化知识源。可服务的方法包在完成对应审阅后进入明确的发布集合，执行任务锁定该集合的版本或文件指纹，不直接读取持续变化的工作树。

真正开发服务时另建运行仓库，负责接口、选用规则、任务状态、模型连接、评议和验收。运行记录、项目私有材料和凭据不进入知识仓库；资料质量改进通过带依据的补丁回到知识源。一次生成输出不能自动升级成权威知识，用户采纳也不等于事实被验证。

本轮只在现有仓库保存此计划，没有创建服务仓库或复制资料。

## 9. 首版技术选择

以下是针对单机、少量项目调用的首版建议，不代表安装或集成已经通过：

| 部分 | 建议 | 选择理由和升级条件 |
|---|---|---|
| 服务接口 | Python＋FastAPI，HTTP／JSON | 复用现有Python构建校验工具；FastAPI提供OpenAPI、JSON Schema和请求数据验证支持。[官方说明](https://fastapi.tiangolo.com/features/) |
| 资料源 | 现有Markdown／JSON＋Git或不可变发布包 | 保持可审阅、可追溯；运行中固定版本，不让知识改动悄悄改变进行中的结论 |
| 任务记录 | SQLite＋本地制品目录 | 单机原型足够简单；由服务管理数据库读写，外部项目只调用API。多主机共享或持续高写入并发时重新选择客户端／服务器数据库。[适用范围](https://sqlite.org/whentouse.html) |
| 工作流 | 明确状态转换＋持久化步骤记录 | 先覆盖单方法和固定两轮评议；内存中的临时后台任务不能承担可靠恢复。复杂分支增长后再比较专用编排框架 |
| 检索 | 领域、用途、状态、版本等过滤＋关键词 | 先建立合格候选集；中文别名和检索召回需要实际测试。语义检索作为检索失败后的增强，不作为首版必需基础设施 |
| 代理接入 | 核心HTTP接口稳定后增加MCP适配 | MCP负责交换工具与上下文；如何使用模型和组织意见仍由服务实现，不能把提供文档的MCP工具当成已经完成咨询。[协议范围](https://modelcontextprotocol.io/docs/learn/architecture) |
| 模型 | 可记录、可替换的获准调用通道 | 实际模型、认证、后台调用能力和计费需要在实施时核对；不默认桌面订阅可充当生产API，不在本轮启用额外收费服务 |

身份校验、项目材料隔离和任务归属属于外部调用的基本边界。首版无需引入DAO、服务网格、常驻专家网络、独立向量数据库或多套同义工作流。

## 10. 怎样证明比直接调用有效

以未用于改写资料的真实任务作对照，并固定输入、可用来源、资源预算和评审标准：

- A：通用模型直接回答，用于衡量整体使用价值。
- B：一个模型读与服务相同的合格方法／证据包，用于区分资料改善和组织过程改善。
- C：本服务选用和执行方法，必要时组织多席评议。

对B与C尤其要控制证据可见范围及预算，否则无法判断收益来自更好的组织还是更多资料／调用。不要因C有更多专家署名就加分。

核心指标：建议是否解决任务、硬约束违反次数、事实与引用支持关系、关键反例遗漏、是否给出可执行的验证行动，以及达到同等质量所需的用户修改量、耗时和资源。用户采纳率作为辅助指标，不能代替正确性；不同任务分别评分，不能用一个总分掩盖关键失败。

复用审计案例检查：方法步骤丢失、作者阶段被替换、来源不足却作确定结论、人物行动限制丢失、世界规则未知。另做答复缺失、过期来源、矛盾意见、重复请求与任务恢复测试。简单任务没有收益时默认走单方法路径；多席路径只有在特定任务中显示增益才扩大使用。

## 11. 推进顺序

1. **确定首批服务任务。** 先以“世界设定评审”和“创作简报／产物评审”贯通两个调用场景，写清输入、输出和失败条件。
2. **建立小范围合格资料集。** 从实际任务反推需要的方法，修复相关审计问题，保留任务级准备状态；不要求先把全库重新蒸馏一遍才开始试验。
3. **做可重放的咨询样板。** 人工按本流程完成一组请求—材料—意见—证据—评审记录，验证服务契约能保留关键信息。原有讨论协议照常执行。
4. **再实现最小服务。** 先单机HTTP、固定资料版本、持久任务记录和单方法路径，再加入已验证的评议流程；不承诺未经测试的吞吐或响应时限。
5. **依据对照结果扩充。** 先扩大有效任务和合格方法覆盖，确有需要再研究跨节点替换、自适应组队及多中心机制。
